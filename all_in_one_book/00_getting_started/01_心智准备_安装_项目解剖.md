## 🎯 30 秒速览

- **Symfony 是什么**：一套**组件（Component）**的集合，加上一个把它们粘在一起的**框架（FrameworkBundle）**。
- **和 Laravel 的最大区别**：Symfony 是**偏"装配"风格**的，几乎每一块都可以替换；Laravel 偏"约定+魔术"风格。
- **本节做什么**：装 PHP 8.4 + Composer + Symfony CLI，跑出 Welcome 页，然后把项目根目录每个东西讲清楚。

## 1. 心智模型：Symfony 在 PHP 世界的哪里

### 1.1 Symfony ≠ 框架

读这本书之前你也许听过"Symfony 框架"这个词。它的全名其实是：

- **Symfony Components**：60 多个互相独立、可以单独 composer require 的库。`HttpFoundation`、`Console`、`Routing`、`Messenger`、`Validator`、`Cache`……
- **Symfony Framework**：用一个叫 `FrameworkBundle` 的 Bundle 把上面这些组件"组装"成一个 MVC 框架。

这就是为什么你会在 `composer.json` 里看到一堆 `symfony/xxx`：它们每个都是独立组件，你装的是**一套组件 + 把它们装在一起的胶水**。

| 如果你见过 | 那么在 Symfony 里对应 |
| --- | --- |
| Laravel `Illuminate\Http\Request` | `Symfony\Component\HttpFoundation\Request`（其实 Laravel 直接用了这个） |
| Laravel `Artisan` | `Symfony\Component\Console`（Laravel 的 Artisan 就是基于它建的） |
| Laravel Facades | Symfony 里**没有等价物**——Symfony 是纯依赖注入，没有 Facade |
| Express.js middleware | Symfony 事件监听器（Kernel 事件）+ Messenger Middleware |
| Spring `@Component` / `@Service` | Symfony 默认把 `src/` 下所有类都当成服务，靠目录而不是注解发现 |

> **新手卡点一号**：读 Laravel 博客会看到"Facade"、"服务提供者"、"Controller as Invokable Class" 这些词，在 Symfony 里**全都不存在**。忘掉它们，重新建立心智模型，不要试图硬套。

### 1.2 一个请求在 Symfony 里走的路（高空视角）

这里先给**轮廓**，02 节会逐步精细化：

```
   浏览器
     │
     ▼
  public/index.php     ← Web 服务器（Nginx / Symfony CLI）把所有请求都交给它
     │
     ▼
   Kernel           ← 实例化"内核"，内核把容器启动
     │
     ▼
  HttpKernel::handle($request)
     │
     ├──→ Router 匹配 URL → 找到控制器（Controller）
     │
     ├──→ 控制器执行 → 返回 Response
     │
     ▼
   浏览器收到响应
```

*图 00.01-B：请求的一生（概览版）。02 节会把每一步再放大。*

只要记住这张图，本书后面一切的 Routing / Controller / Event / Security 都是在**这条路上的某一段**做文章。

### 1.3 三个命令，三件职责

新手最容易混淆的一组命令：

| 命令 | 它是谁 | 它管什么 | 典型场景 |
| --- | --- | --- | --- |
| `composer ...` | **PHP 包管理器**（通用，不专属 Symfony） | 装 / 升 / 卸 PHP 依赖、处理 `composer.json` | `composer require symfony/mailer` |
| `symfony ...` | **Symfony CLI**（可选的一个 Go 二进制） | 本地 HTTPS web 服务器、PHP 版本切换、Docker 集成、Flex | `symfony server:start` |
| `php bin/console ...` | **你项目自己的** Console 入口（一个 PHP 脚本） | 框架内的所有命令：路由、容器、缓存、迁移、测试…… | `php bin/console debug:router` |

口诀：

- 跟**依赖**打交道 → `composer`
- 跟**机器 / HTTPS / 本地服务**打交道 → `symfony`
- 跟**项目本身**（路由、实体、配置、缓存）打交道 → `php bin/console`

> **常见误区**：想跑迁移结果敲了 `composer migrate`——composer 根本没这命令。想启动服务结果敲了 `php bin/console serve`——bin/console 里也没有。

`symfony console xxx` 是 Symfony CLI 对 `php bin/console xxx` 的代理，两者等价，全书为了兼容**不装 Symfony CLI** 的读者，统一写 `php bin/console xxx`。

## 2. 快速上手（5 分钟版）：跑出第一个页面

### 2.1 前置环境

官方 `setup.rst` 在 8.0 分支里的要求是：

- **PHP 8.4 或更高**，启用扩展：`Ctype`、`iconv`、`PCRE`、`Session`、`SimpleXML`、`Tokenizer`（PHP 8 的默认安装已经都带了）
- **Composer 2.x**
- **Symfony CLI**（可选但强烈推荐）

检查 PHP：

```bash
$ php -v
PHP 8.4.3 (cli) ...
```

如果版本低于 8.4，装 Symfony 8.0 的 `composer create-project` 会直接拒绝（后文 `composer require` 给出的报错就是这个原因）。

### 2.2 安装 Symfony CLI

不同平台的安装方式：

```bash
# macOS / Linux：官方一键脚本
$ curl -sS https://get.symfony.com/cli/installer | bash
$ export PATH="$HOME/.symfony5/bin:$PATH"   # 根据安装脚本的提示调整

# macOS Homebrew
$ brew install symfony-cli/tap/symfony-cli

# Windows（Scoop）
$ scoop install symfony-cli
```

装完之后：

```bash
$ symfony check:requirements
```

这条命令会把你机器的 PHP 版本、扩展、权限全过一遍，缺什么直接告诉你。比你自己 `php -m | grep xxx` 地挨个查靠谱得多。

### 2.3 创建项目

本书从 00 章起就用贯穿项目 `bookstore`：

```bash
$ symfony new bookstore --version="8.0.*" --webapp
$ cd bookstore
```

**两个选项的含义**：

- `--version="8.0.*"`：锁定 Symfony 8.0 系列。不写的话默认拉最新稳定版（可能是 8.x 以上）。
- `--webapp`：**关键选项**。加了它会额外装 Twig / Doctrine / Form / Validator / Mailer 等"做 Web 应用几乎一定会用上的"一整套。不加的话就是 Symfony "微骨架"（skeleton），只有 HTTP + Router + 容器，适合做纯 API 或 CLI 工具。

> **新手卡点二号**：很多博客文章在讲"安装"时没写 `--webapp`，导致读者跟着敲下去后，后面讲到 Twig / Doctrine 就报 "class not found"。忘记加 `--webapp` **不是报错**，是"后面用到了才发现没装"，痛苦指数更高。本书一律用 `--webapp`。

### 2.4 启动本地服务器并打开

```bash
$ symfony server:start
```

终端会打印：

```
[OK] Web server listening
      The Web server is using PHP CLI 8.4.x
      https://127.0.0.1:8000
```

打开 `https://127.0.0.1:8000`（第一次打开浏览器会提示证书不受信任，这是 Symfony CLI 自签的本地 HTTPS 证书；本地开发可以忽略或执行 `symfony server:ca:install` 一劳永逸）。

你应该看到 Symfony 的 Welcome 欢迎页。如果没看到，跳到本节末尾的「小结与应急」。

### 2.5 写第一个真正的路由

Welcome 页是 Symfony 自带的"当你没定义任何路由时"的兜底页面。我们来写一个自己的：

```php
<?php
// src/Controller/HelloController.php

namespace App\Controller;

use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class HelloController
{
    #[Route('/hello/{name}', name: 'hello', defaults: ['name' => 'world'])]
    public function __invoke(string $name): Response
    {
        return new Response(
            '<h1>Hello, '.htmlspecialchars($name).'!</h1>'
        );
    }
}
```

保存后**不用重启服务器**——Symfony CLI 会自动感知变动。浏览器打开：

- `https://127.0.0.1:8000/hello` → 显示 `Hello, world!`
- `https://127.0.0.1:8000/hello/symfony` → 显示 `Hello, symfony!`

恭喜——你已经在 Symfony 里跑了一条自己的路由了。

**到底刚才发生了什么？**（先直觉理解，02 节会细讲）

1. 浏览器把 `GET /hello/symfony` 发到 `public/index.php`。
2. Symfony 内核启动，从 `src/Controller/` 下**自动发现**所有带 `#[Route]` 的类——这就是为什么你不用手动"注册"控制器。
3. `Router` 把 URL `/hello/symfony` 匹配到 `HelloController::__invoke`，`{name}` 被解析成 `"symfony"`，作为方法参数传入。
4. 方法返回一个 `Response` 对象，Symfony 把它写回给浏览器。

> **新手卡点三号**：很多框架你得在某个"路由文件"里手动写一行才算注册了。Symfony 默认**扫描 `src/Controller/`**。这在 `config/routes.yaml` 里可以看到：
>
> ```yaml
> # config/routes.yaml
> controllers:
>     resource:
>         path: ../src/Controller/
>         namespace: App\Controller
>     type: attribute
> ```
>
> 这条 YAML 才是让 `#[Route]` 生效的真正钥匙。删掉它，你的属性就再也不生效了。

## 3. 日常应用（30 分钟版）：项目骨架解剖

这是整节最有信息密度的一块。一个刚创建的 `bookstore` 目录长这样：

```
bookstore/
├── .env                     ← 默认环境变量（进 git）
├── .env.dev                 ← dev 环境额外变量（进 git）
├── .env.test                ← test 环境额外变量（进 git）
├── .env.local               ← 本机私有覆盖（不进 git）← 你放数据库密码的地方
├── .gitignore
├── bin/
│   └── console              ← 项目自带 CLI 入口，几乎是全书最常用的命令
├── composer.json            ← 依赖声明与脚本
├── composer.lock
├── config/                  ← 所有配置
│   ├── bundles.php          ← 注册启用哪些 Bundle（手动加新 Bundle 时要改）
│   ├── packages/            ← 每个 Bundle 的配置各占一个 YAML
│   │   ├── framework.yaml
│   │   ├── doctrine.yaml
│   │   ├── security.yaml
│   │   └── ...
│   ├── routes.yaml          ← 路由发现策略
│   ├── routes/              ← 其它路由文件（框架自带 / 你自加）
│   ├── services.yaml        ← 服务容器的"入口"配置
│   └── preload.php          ← opcache preload 列表（prod 优化）
├── public/
│   ├── index.php            ← Web 请求的唯一入口
│   └── .htaccess            ← Apache 用（Nginx 则需另写 rewrite）
├── src/                     ← **你写的代码都在这**
│   ├── Controller/
│   ├── Entity/              ← 装了 Doctrine 后自带
│   ├── Repository/
│   ├── Form/                ← 装了 Form 后自带
│   ├── Kernel.php           ← 默认的内核类，绝大多数项目从来不用改它
│   └── ...
├── templates/               ← Twig 模板（装了 Twig 后自带）
│   └── base.html.twig
├── translations/            ← 翻译文件（i18n）
├── tests/                   ← PHPUnit 测试
├── var/
│   ├── cache/               ← **所有编译产物**（容器编译、路由匹配器、Twig 编译）
│   └── log/                 ← 日志
├── vendor/                  ← Composer 装下来的依赖（绝不进 git）
├── assets/                  ← AssetMapper（8.x 默认）的源资源
├── importmap.php            ← 前端 importmap 声明
├── migrations/              ← Doctrine Migrations 生成的迁移文件
└── symfony.lock             ← Flex 已装 recipe 的锁文件（进 git）
```

### 3.1 最核心的六个目录 / 文件

记住这六个，其它的都是这六个的补充：

#### ① `public/index.php`——**前门**

所有 Web 请求都从这一个文件进来。它做三件事：

1. 加载 `.env`
2. 实例化 `Kernel`
3. 把 `Request` 交给 `Kernel::handle()`，把返回的 `Response` 发回去

刚开的项目里它只有 10 行左右，**你永远不需要改它**。真的不要改。

#### ② `src/Kernel.php`——**你的项目自己的内核**

它继承自 `Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait`。它是**你项目里唯一的 "Symfony 入口类"**，负责告诉框架：

- 启用哪些 Bundle（读 `config/bundles.php`）
- 配置文件在哪里（`config/packages/`）
- 路由在哪里（`config/routes*`）

90% 的项目**永远不改它**。需要改的情况是：你要改缓存目录、日志目录，或者要接入一个特别奇怪的 Bundle 加载方式——这属于高级用法，后面 20 章会专门讲。

#### ③ `config/` —— **配置中心**

规矩：

- `config/packages/*.yaml` 里的配置，对 **所有环境** 生效
- `config/packages/dev/*.yaml` 只对 `APP_ENV=dev` 生效
- `config/packages/prod/*.yaml` 只对 `APP_ENV=prod` 生效
- `config/packages/test/*.yaml` 只对 `APP_ENV=test` 生效

"配置覆盖"的细节在 11 章讲完整。现在只要知道：**在 prod 里生效的配置 ≠ 在 dev 里生效的配置**。

#### ④ `src/` —— **你的代码**

Symfony 的默认 `services.yaml` 里有这么一段（打开看看）：

```yaml
# config/services.yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true

    App\:
        resource: '../src/'
        exclude:
            - '../src/DependencyInjection/'
            - '../src/Entity/'
            - '../src/Kernel.php'
```

这几行的意思是：

- `App\` 命名空间对应的目录是 `src/`
- 这个目录下除了 `Entity/`（数据容器不该当服务）、`DependencyInjection/`（Bundle 内部用）、`Kernel.php`（内核不是业务服务）之外，**所有类都会被自动注册为服务**
- `autowire: true` 意味着它们的构造器参数会按类型自动注入
- `autoconfigure: true` 意味着它们会按"实现了哪个接口"自动打上对应标签（例如实现了 `EventSubscriberInterface` 就自动成为事件订阅者）

> **新手卡点四号**：你不用手动"注册"任何控制器、监听器、命令。把类扔进 `src/` 的合适子目录，让它实现合适的接口或带上 `#[As*]` 属性，它就自动接上了。DI 容器是这本书最重的一章（第 9 章），那一章会把这个"自动"的每一步都展开。

#### ⑤ `var/cache/` —— **编译产物，不是源码**

这个目录里装的是：

- 编译后的 DI 容器（纯 PHP 代码）
- Twig 编译出的 PHP 类
- 路由匹配器
- 元数据缓存（Doctrine / Serializer / Form）

**关键事实**：它**完全是可再生**的。任何时候看到诡异现象，第一反应就是：

```bash
$ rm -rf var/cache/*
# 或者
$ php bin/console cache:clear
```

这是 Symfony 开发者的"重启大法"。

> **新手卡点五号**：改了 YAML 配置但没生效？十次里有九次是 dev 环境下的配置缓存。dev 环境理论上会自动刷新，但在 Docker / 挂载卷 / Windows 文件系统下可能感知不到文件变动。**先清缓存再排查**。

#### ⑥ `vendor/` —— **依赖的家**

- Composer 装下来的第三方库全在这里。
- **绝不提交进 git**（`.gitignore` 里已经默认忽略）。
- 部署时要么在服务器上 `composer install`，要么用 CI 打包。

### 3.2 其他文件与目录（次要但要眼熟）

| 路径 | 一句话解释 |
| --- | --- |
| `.env` | 默认环境变量（如 `APP_ENV=dev`、`DATABASE_URL`）。**进 git**——作为"模板"让别人知道你有哪些变量 |
| `.env.local` | 你本机的私有覆盖（真实密码、端口）。**不进 git** |
| `.env.test` | 跑 `phpunit` 时会自动加载的变量 |
| `symfony.lock` | Symfony Flex 记录已安装 recipe 的文件。**进 git** |
| `config/bundles.php` | 哪些 Bundle 在哪些环境启用。`composer require` 装新 Bundle 时 Flex 会自动改这里 |
| `config/preload.php` | opcache preload 用。prod 优化专用 |
| `assets/`、`importmap.php` | AssetMapper（Symfony 8 默认的前端资源方案）。21 章讲 |
| `migrations/` | `make:migration` 生成的 DB 迁移文件。07 章讲 |
| `translations/` | 翻译文件。本书 11 章会扫一遍，不单独列章 |
| `bin/console` | 封装了 `Console` 组件的 PHP 脚本，是 `Kernel::boot()` + 运行命令的入口 |
| `bin/phpunit` | 装了 PHPUnit Bridge 后 Flex 会自动生成的测试入口（19 章讲） |

### 3.3 配置项逐项讲解：`services.yaml` 默认内容

默认的 `config/services.yaml` 全文（Symfony 8.0 `--webapp` 生成版）：

```yaml
# config/services.yaml
parameters:

services:
    # default configuration for services in *this* file
    _defaults:
        autowire: true      # Automatically injects dependencies in your services.
        autoconfigure: true # Automatically registers your services as commands, event subscribers, etc.

    # makes classes in src/ available to be used as services
    # this creates a service per class whose id is the fully-qualified class name
    App\:
        resource: '../src/'
        exclude:
            - '../src/DependencyInjection/'
            - '../src/Entity/'
            - '../src/Kernel.php'

    # add more service definitions when explicit configuration is needed
    # please note that last definitions always *replace* previous ones
```

逐块解释：

| 片段 | 它是什么 | 何时需要改 | 不改的默认行为 |
| --- | --- | --- | --- |
| `parameters:` | 容器参数区。你可以在这放 `app.default_locale: zh_CN` 之类的值 | 你要定义一些"代码里能读到的常量" | 为空 |
| `_defaults.autowire: true` | 对本文件后续所有服务生效的默认值：按类型自动注入 | 你想在某个特殊服务上关掉它（单独写 `autowire: false`） | 开启 |
| `_defaults.autoconfigure: true` | 同上，但管"按接口打标签" | 极少需要改 | 开启 |
| `App\: resource: '../src/'` | 把 `src/` 下所有类一次性注册为服务 | 你要排除 / 新增某个目录 | 扫全部 |
| `exclude: ...` | 哪些目录下的类**不**注册为服务 | 你新建了一个"不该当服务"的目录（如 `src/Dto/`、`src/Exception/`） | 只排除默认那三个 |

> **何时要改 `services.yaml`**：
> - 要显式给某个服务传一个字符串 / int 参数（autowire 解决不了的场景）——这时你会新增一个 `App\SomeService: arguments: ...` 块
> - 要给某个服务打自定义标签（当你不想用 `#[AsTaggedItem]` 属性时）
> - 要排除更多目录（新增了 `src/Dto/`、`src/ValueObject/` 这类纯数据类）
>
> 09 章会把每种场景都写一个完整例子。

## 4. 进阶：三种"启动本地服务器"方案的对比

官方 `setup.rst` 里暗示了三种，新手选型时容易懵。明确给出对比：

| 方案 | 启动命令 | 优点 | 缺点 | 什么时候选 |
| --- | --- | --- | --- | --- |
| **Symfony CLI 本地服务器** | `symfony server:start` | 自带 HTTPS、HTTP/2、自动发现 PHP-FPM、零配置 | 需要装 Symfony CLI | **本书全程推荐**，新手首选 |
| **PHP 内置服务器** | `php -S 127.0.0.1:8000 -t public/` | 零依赖 | 不支持 HTTPS、不支持并发、易被 PHP 路由误导 | 不得已时（装不上 Symfony CLI） |
| **Docker + symfony/docker** | `docker compose up` | 接近生产环境 | 学习成本高、Windows 挂载慢 | 团队统一开发环境、部署章（21 章）详讲 |

**推荐顺序**：Symfony CLI（本书主线）→ Docker（21 章上线前再切）→ PHP 内置服务器（应急）。

## 5. 深潜：`public/index.php` 干了什么

打开 `public/index.php`（`--webapp` 版）：

```php
<?php
// public/index.php

use App\Kernel;

require_once dirname(__DIR__).'/vendor/autoload_runtime.php';

return function (array $context) {
    return new Kernel($context['APP_ENV'], (bool) $context['APP_DEBUG']);
};
```

关键点：

1. `require vendor/autoload_runtime.php`：这是 `symfony/runtime` 组件装上后 Flex 生成的文件。它做了**两件事**：
   - 加载 Composer 自动加载器
   - 把你返回的 closure **接管**——实际的 `$request = Request::createFromGlobals()` → `$kernel->handle($request)` → `$response->send()` → `$kernel->terminate($request, $response)` **不是你写的**，是 Runtime 组件内部干的。
2. `new Kernel($context['APP_ENV'], (bool) $context['APP_DEBUG'])`：内核的两个关键参数来自**环境变量**（由 `Dotenv` 组件从 `.env*` 系列文件加载）：
   - `APP_ENV`：`dev` / `prod` / `test`，决定加载哪些配置
   - `APP_DEBUG`：`0` / `1`，决定是否启用 Profiler、是否重编容器、错误页是否显示堆栈

**换句话说**：你以为 `index.php` 就 5 行什么都没做，其实它通过 `autoload_runtime.php` 委托了整条请求生命周期。02 节会带你追进 `vendor/symfony/runtime/` 看这条链。

## 7. 常见报错图鉴

### 报错 1：`Your Composer dependencies require a PHP version ">= 8.4.0"`

- **它在说什么**：你机器上的 PHP 版本低于 Symfony 8.0 要求
- **为什么出现**：`composer.json` 里 Symfony 8.0 声明了 `"php": ">=8.4"`，composer 在 `install` / `require` 时做硬检查
- **怎么修（按推荐顺序）**：
  1. 升级 PHP 到 8.4+（macOS：`brew install php@8.4`；Linux：用 Ondřej Surý 的 PPA；Windows：从 `windows.php.net` 下载）
  2. 如果必须留在低版本 PHP（例如服务器暂不能升），那就**必须降 Symfony 版本**：装 Symfony 7.x
  3. 用 `composer install --ignore-platform-req=php` **是下策**，会在运行时遇到未知的语法错误（Symfony 8.0 用了 PHP 8.4 的新语法）
- **怎么预防**：开发机装 Symfony CLI 后跑 `symfony check:requirements`，在装任何依赖之前先对齐版本

### 报错 2：`The web server is already running on port 8000`

- **它在说什么**：8000 端口被占用
- **为什么出现**：上一次没 Ctrl+C 正常退出；或另一个 Symfony 项目也起了服务器；或别的进程（Python、Node）在用
- **怎么修**：
  1. `symfony server:stop`——Symfony CLI 会干净停掉自己启过的进程
  2. 改端口：`symfony server:start --port=8001`
  3. 查是谁占的：macOS/Linux 用 `lsof -i :8000`，Windows 用 `netstat -ano | findstr 8000`
- **怎么预防**：本机多项目时，给每个项目在 `.env.local` 里配不同默认端口（Symfony CLI 会读 `SYMFONY_PORT`）

### 报错 3：`Unable to write in the cache directory (/.../var/cache/dev)`

- **它在说什么**：PHP 进程没权限写 `var/cache/`
- **为什么出现**：多见于把项目放在某些特殊挂载目录、或 Docker 里 UID 不匹配、或 macOS 下的 `/Volumes/` 外挂卷
- **怎么修**：
  1. `chmod -R u+w var/`
  2. 如果是 Docker，确保容器里的用户 UID 和宿主机你的用户 UID 一致（`docker run --user $(id -u):$(id -g) ...`）
  3. 实在搞不定：把 `var/` 目录改到 `/tmp`——修改 `src/Kernel.php` 重写 `getCacheDir()` 和 `getLogDir()`（不推荐，是终极解法）
- **怎么预防**：按官方 `setup/file_permissions.rst` 的指南配 ACL：`setfacl -R -m u:www-data:rwX -m u:$(whoami):rwX var/`

### 报错 4：页面打开是一片空白 / 500 但浏览器没堆栈

- **它在说什么**：prod 环境下 Symfony 的兜底错误页被触发，但你以为是 dev
- **为什么出现**：`.env` 或环境变量里 `APP_ENV=prod`，或 `APP_DEBUG=0`
- **怎么修**：
  1. 确认 `.env.local` 里 `APP_ENV=dev` 且 `APP_DEBUG=1`
  2. 看 `var/log/prod.log`——prod 下的错误会进日志（dev 下进 `dev.log`）
  3. 如果是 CLI 里跑 Symfony CLI server，跑 `symfony server:log` 能实时看所有请求和 PHP 错误
- **怎么预防**：在 shell profile 里 `export APP_ENV=dev` 之前，先确认项目 `.env` 的默认值

### 报错 5：`Class "App\Controller\HelloController" not found` 或者路由找不到

- **它在说什么**：类存在但没被发现，或路由没被扫描到
- **为什么出现**（按概率排序）：
  1. 命名空间写错（`namespace App\Controller` 少个反斜杠或多字符）
  2. 文件放在 `src/Controller/` 之外（比如放进了 `app/Controller/`）
  3. 改了 `config/routes.yaml` 里的 `path: ../src/Controller/` 指错了
  4. 缓存没清
- **怎么修**：
  1. `php bin/console debug:router` 看路由有没有登记——没登记就是路由发现出了问题
  2. `php bin/console debug:container App\Controller\HelloController` 看服务有没有注册——没注册就是服务发现出了问题
  3. `php bin/console cache:clear`
- **怎么预防**：用 IDE 的 Symfony 插件（PHPStorm 的 Symfony Support 插件 / VS Code 的 Symfony for VSCode），它会在你命名空间写错时立刻标红

### 报错 6：`symfony: command not found`

- **它在说什么**：Symfony CLI 装了但没进 `PATH`
- **为什么出现**：官方安装脚本把二进制放到 `$HOME/.symfony5/bin`，默认没加到 `PATH`
- **怎么修**：
  1. `export PATH="$HOME/.symfony5/bin:$PATH"`（临时）
  2. 把上面这行加到 `~/.bashrc` / `~/.zshrc`（永久）
  3. 或者直接 `brew install symfony-cli/tap/symfony-cli`（macOS），brew 会自动处理 PATH
- **怎么预防**：安装脚本最后一行它会告诉你怎么做——看完它再关终端

## 8. 陷阱与反模式

- ❌ **把 `vendor/` 提交进 git**（后果：仓库膨胀到 GB 级、不同开发者拉下来版本不一致、部署时 composer 没解决真正的依赖冲突）
  ✅ `.gitignore` 里默认就排除了 `vendor/`，别手贱删掉这条
- ❌ **把 `.env.local` 提交进 git**（后果：数据库密码 / 第三方 API key 泄露）
  ✅ `.gitignore` 里默认就排除了 `.env.local` 与 `.env.*.local`
- ❌ **把 `var/` 整个提交**（后果：缓存里有旧的容器编译产物，会和别人机器上的环境冲突，造成"玄学 bug"）
  ✅ 默认 `.gitignore` 也已排除
- ❌ **忘了加 `--webapp`，后续想用 Twig / Doctrine 时又临时 `composer require webapp`**（不是错误，但 `composer require webapp` 的 Flex recipe 会在 `config/` 下创建一堆新文件，如果你中间自己改过同名文件会碰到合并冲突）
  ✅ 初始化时就想清楚：要做 Web 应用就加 `--webapp`
- ❌ **用 `php -S` 在 `public/` 里起服务**（后果：子路径如 `/books/1` 走到了 PHP 内置服务器自己的路由，把 `index.php` 跳过，返回 404）
  ✅ `php -S 127.0.0.1:8000 -t public/ public/index.php`——最后一个参数把 `index.php` 当"router 脚本"，才能正确 rewrite
  ✅ 或者干脆用 `symfony server:start`
- ❌ **`cache:clear` 跑成了 `prod` 环境**（后果：误清生产缓存，下一次请求全部 cold start；不危险但让客户愣几秒）
  ✅ `cache:clear --env=dev`——在生产上临时调试时**显式**指定环境，别依赖默认

## 12. FAQ

**Q1：我能在 Symfony 8 里继续用注解 `@Route` 吗？**
A：不能。Symfony 8 已**移除** annotation 支持，全部走 PHP 原生 Attribute `#[Route]`。如果你看的教程里写 `@Route(...)`，那就是老版本内容。

**Q2：`symfony new` 和 `composer create-project symfony/skeleton` 有啥区别？**
A：前者是 Symfony CLI 的封装，省你手动打一串；后者是 composer 原生命令，在没装 Symfony CLI 的环境下可以用。**最终装出来的项目几乎一致**。CLI 版会额外注入一些 git 初始化的小便利。

**Q3：为什么 Welcome 页是 `https` 而不是 `http`？**
A：Symfony CLI 启动本地服务器时默认用自签证书开 HTTPS，这样你在本地开发时就能用和生产一样的协议（有些 cookie、Service Worker、OAuth 回调必须 HTTPS）。跑一次 `symfony server:ca:install` 把 CA 证书装进系统信任库，警告就消失了。

**Q4：为什么一创建项目就有这么多文件？我记得 Slim 只有 3 个文件。**
A：因为 `--webapp` 把一个生产级 Web 应用的常用组件（Twig / Doctrine / Form / Validator / Security / Mailer / Messenger / Notifier）都装上了。不加 `--webapp` 的微骨架只有十来个文件。选型建议见第 6 节选择指南。

**Q5：这个项目可以不用 Doctrine 吗？我想用原生 PDO。**
A：完全可以。`composer remove doctrine/doctrine-bundle doctrine/orm` 就能彻底拆掉。本书 07 章默认用 Doctrine，但凡是非 Doctrine 的场景会在各章给出独立方案。

**Q6：我想用 PostgreSQL 但 `--webapp` 默认装的是不是只支持 MySQL？**
A：`--webapp` 装的是 `doctrine-bundle`，它抽象在 DBAL 之上，支持 MySQL / MariaDB / PostgreSQL / SQLite / SQL Server。切数据库只要改 `.env` 里的 `DATABASE_URL`，连 composer 依赖都不用动（但如果你用 PG 就得本机装 `pdo_pgsql` 扩展）。

**Q7：`.env`、`.env.dev`、`.env.local`、`.env.local.dist`——到底哪个优先级最高？**
A：这是 11 章的专题。短答案：**越"local"越优先，test 环境会整组用 `.env.test*`**。完整加载顺序：`.env` < `.env.{APP_ENV}` < `.env.local` < `.env.{APP_ENV}.local` < 真实环境变量。

**Q8：我想给项目改名，从 bookstore 改成别的，怎么弄？**
A：Symfony 项目的目录名和代码名是解耦的——`bookstore/` 这个目录名只是你硬盘上的一个文件夹。你改名 `mv bookstore my_shop` 完全不影响。代码里默认命名空间一律是 `App\`，也不跟目录名绑定。唯一有影响的是一些默认 cookie 名 / session 名里会出现目录名，但不影响功能。

**Q9：公司服务器是 PHP 7.4，那我不能用 Symfony 8 了？**
A：不能。Symfony 8 最低 PHP 8.4，PHP 7.4 早已 EOL。你有两个选：说服运维升级 PHP，或者降到 Symfony 6.x LTS（能跑 PHP 8.1）。这本书的大多数概念在 6.x/7.x 仍然适用，但具体代码不保证。

**Q10：我能把 `src/Controller/` 改成 `app/Controller/` 吗？**
A：技术上能（改 `services.yaml` 和 `routes.yaml` 里的 `resource` 路径），但**不建议**。Symfony 世界里 `src/` 是强约定，Flex recipe、生态的 IDE 插件、教程、开源 Bundle 都默认 `src/`。你改了它们都得重配。**除非有真正不可抗力，跟着约定走。**

**Q11：改了 YAML 配置没生效怎么办？**
A：九成是缓存。`php bin/console cache:clear` 之后再试。剩下一成是：你改错了环境对应的目录（比如改了 `config/packages/prod/` 但你在 `dev` 里测），或者 `.yaml` 语法错误让 Symfony 静默回退到缓存版本（这时看 `var/log/dev.log` 会有警告）。

**Q12：有没有"Symfony 8 vs 7 vs 6" 的差异快表？**
A：有。已收录在 `PROGRESS.md` 的「语焉不详清单」里，会在后续章节里的附录中逐步填满。现阶段只要记住：**Google 到的 2023 年之前的文章默认当作"老版本"看，任何 `@Route` 注解、`Doctrine\Common\Annotations`、`SensioFrameworkExtraBundle` 都是旧世界**。

        - '../src/Controller/'
```

结果：控制器类不再被注册为服务。访问 `/hello` 时 Symfony 会报 "Controller ... is neither a service nor a Closure"。这证明**控制器必须先是服务**，而这是由 `services.yaml` 的资源扫描决定的——不是 `#[Route]` 自动打的服务标签。

这是第 9 章最重要的先修知识之一：**`#[Route]` 只决定 URL 和方法的对应，不决定类是不是服务**。

</details>
